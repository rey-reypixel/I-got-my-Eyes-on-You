PROJECT DIAGRAMS SPECIFICATION
================================
A complete list of every diagram this project needs, why it needs it, and
exactly what should be drawn. Part 1 covers the 8 figures referenced by
number (Fig. 1-8) in paper/IEEE_paper_final.tex -- these are not optional,
the paper's text points at them and a reviewer will look for them. Part 2
covers diagrams that are not cited in the paper but are worth having for the
demo, the oral defense, and general project documentation.

STATUS (2026-07-22): Part 1's 8 figures now exist under paper/figures/ and
are wired into IEEE_paper_final.tex via \includesvg / \includegraphics.
Fig. 1, 3, 4, 6, 7, 8 are hand-authored SVGs styled to match draw.io's
default palette/fonts/arrow conventions (they are plain SVG, not exported
from the actual draw.io app -- open them in draw.io/Inkscape/a browser to
confirm before relying on the visual match, and feel free to import and
refine them further in draw.io itself, since they're valid, editable SVG).
Fig. 2 and Fig. 5 are real captures: generated by actually running this
project's own pipeline code (letterbox_resize, roi_polygon, is_inside_polygon)
against real frames from AVSS 2007 footage already in data/raw, not drawn or
staged -- Fig. 2 even landed on a real, previously-logged INTRUDER frame
(demo_events.db run_id=15, frame 2205). Part 2's diagrams below are still
just specifications; none of those have been produced yet.

Suggested tooling, once per diagram type, so it isn't repeated below:
  - Block/architecture/flow/state diagrams: draw.io (diagrams.net, free,
    exports clean SVG/PNG, has an IEEE-friendly rectangular-block aesthetic
    already built in) or Mermaid (mermaid.js -- fast to iterate in text form
    first, then export, and renders natively in a lot of tooling if a live
    version is ever wanted instead of a static image).
  - Charts (bar/scatter/line): matplotlib (Python), since the raw numbers
    already live in benchmark/*.csv and this project is already a Python
    codebase -- no reason to hand-build these in a general graphics tool.
  - Annotated video frames (before/after, ROI overlay, dataset examples):
    a real screenshot from the live pipeline (main.py --no-show, or with the
    window showing), annotated afterward if needed (arrows, crop, labels) in
    any basic image editor. These should be REAL frames from REAL footage
    already in data/raw, not mockups -- the whole point of several of these
    figures is showing something that actually happened.

PART 1 -- FIGURES REQUIRED BY THE PAPER (Fig. 1 through Fig. 8)
--------------------------------------------------------------------------------

FIG. 1 -- Overall System Architecture
--------------------------------------
Referenced: Section III (opening paragraph, before III-A).
Type: Block diagram (left-to-right or top-to-bottom pipeline).
Tool: draw.io.
Content: A single horizontal (or vertical) chain of boxes:
  Video Input -> Letterbox Preprocessing (Section III-E) -> YOLOv8n Detection
  -> ByteTrack Association -> [branches into three parallel boxes at this
  point, since all three objectives consume the same tracked detections]:
    (a) Objective 1: Unauthorized Access (ROI polygon test)
    (b) Objective 2: Abandoned Objects (3-state machine)
    (c) Objective 3: Suspicious Activity (kinematic + gated pose signal)
  -> [the three branches recombine into] Overlay Rendering + Alert Output
  -> [a side branch, drawn going down/aside from the recombine point, not
      inline in the hot path, to visually communicate it's decoupled]:
     Event Log (SQLite) -> MCP Server (separate process, reads only)
Labels to include: which section of the paper documents each box (e.g.
"III-A" under the YOLOv8n/ByteTrack box, "III-B/C/D" under the three
objective boxes, "III-G" under the event log/MCP branch). This lets a reader
map the diagram straight back to the text.
Caption (once drawn): "Fig. 1. Overall system architecture. Detections flow
through a shared perception foundation before being consumed independently
by three reasoning objectives; the event log and MCP server are decoupled
from the live detection loop by design (Section III-G)."

FIG. 2 -- ROI Polygon / Point-in-Polygon Containment
-------------------------------------------------------
Referenced: Section III-B.
Type: Annotated real video frame.
Tool: Real screenshot (any unauthorised_access clip with the ROI polygon
active, e.g. an AVSS platform-edge clip, per config.json's roi_polygon),
annotated afterward.
Content: One frame showing the drawn ROI polygon outline overlaid on the
actual video (the live pipeline already draws this if roi_polygon is
active -- capture it directly, don't redraw it from scratch), with:
  - The polygon boundary highlighted/traced if not already visually distinct.
  - One tracked person's foot coordinate marked with a dot or crosshair,
    with a short label "(x, y) tested against polygon" pointing to it.
  - If possible, show one frame where the person is inside (label INTRUDER
    in the caption or a callout) alongside describing the outside case in
    the caption text, rather than needing two separate figures for this.
Caption: "Fig. 2. Region-of-interest polygon containment test. A tracked
person's foot coordinate is evaluated against the configured restricted-zone
polygon via ray-casting each frame (Section III-B)."

FIG. 3 -- Abandoned-Object Three-State Machine
--------------------------------------------------
Referenced: Section III-C.
Type: State diagram (not a video frame -- this is the one truly abstract
diagram among the required 8, and it should look like a classic state
machine diagram, not a screenshot).
Tool: draw.io or Mermaid (`stateDiagram-v2` renders this cleanly in Mermaid
if a quick text-first draft is wanted before committing to draw.io).
Content: Three circular/rounded-rectangle states arranged left to right or
in a triangle:
  ATTENDED --[distance > d_disconnect]--> WARNING
  WARNING --[distance < d_reconnect]--> ATTENDED
  WARNING --[timer >= th_frames]--> ABANDONED
  ABANDONED --[distance < d_reconnect]--> ATTENDED
Label the two distance thresholds explicitly on their arrows (d_disconnect,
d_reconnect) and note directly on the diagram that d_disconnect > d_reconnect
(this asymmetry IS the hysteresis, and is worth making visually obvious, not
just stated in the caption). A small annotation near WARNING noting "timer
increments each frame in this state" completes the picture.
Caption: "Fig. 3. Abandoned-object state machine. Hysteresis
(d_disconnect > d_reconnect) prevents flicker at the proximity threshold
boundary (Section III-C)."

FIG. 4 -- Suspicious-Activity Dual-Signal Gating Architecture
------------------------------------------------------------------
Referenced: Section III-D.
Type: Flowchart with a conditional gate, not a plain linear pipeline.
Tool: draw.io.
Content: Two parallel input paths merging into one output:
  Path A (always running): Centroid position (per frame) -> normalize by
    perspective-corrected body height -> smooth over rolling window ->
    kinematic_suspicious_flag
  Path B (conditionally running): Centroid stationary for >= 12 frames?
    -> [only if yes] -> Pose model inference (yolov8n-pose, lazily loaded)
    -> wrist/elbow keypoints -> variance relative to torso reference ->
    EMA smoothing -> limb_suspicious_flag
  Both flags feed into: resolve_person_state() priority resolution (this is
  a good place to also show the OTHER two flags this function resolves,
  intruder_flag and panic_flag, and the fixed priority order INTRUDER >
  PANIC > SUSPICIOUS_ACTIVITY > NORMAL -- see the note on a possible Fig. 9
  in Part 2 below if this deserves its own separate diagram instead of being
  folded into Fig. 4's right edge).
The gate itself (the diamond/decision box on Path B) is the most important
visual element here -- it's what makes this "compute-gated" rather than
"always-on," and that distinction is the whole point of Section III-D's
design.
Caption: "Fig. 4. Suspicious-activity dual-signal architecture. The
pose-based limb-motion path is gated on sustained centroid stillness to
avoid doubling inference cost on every tracked person every frame
(Section III-D)."

FIG. 5 -- Letterbox Preprocessing: Before/After
----------------------------------------------------
Referenced: Section III-E.
Type: Side-by-side annotated frame comparison.
Tool: Real frame from any non-square source clip (e.g. anything at 720x480
or similar under data/raw), processed two ways: once through the OLD naive
stretch-resize (this code path no longer exists in src/detection.py -- it
would need to be reconstructed with a two-line throwaway script calling
cv2.resize(frame, (640, 640)) directly, since letterbox_resize is what
actually ships now) and once through the current letterbox_resize function.
Content: Two panels side by side, same source frame:
  Left: naively stretched to 640x640 -- a person in this panel should look
  visibly "squashed" (anisotropically distorted) compared to the right panel.
  Right: letterbox-resized to 640x640 -- gray padding bars visible on
  whichever axis has slack, person proportions preserved.
Label each panel clearly ("Naive stretch resize" / "Letterbox resize
(used)") and, if the source frame is 320x240 or similar, annotate the exact
distortion factors on the left panel (e.g. "2.0x horizontal, 2.667x
vertical" per the paper's own example) so the caption's numbers are
traceable directly to the image.
Caption: "Fig. 5. Letterbox preprocessing compared to a naive stretch
resize. The stretch panel anisotropically distorts human proportions on
non-square source video; the letterbox panel preserves aspect ratio at the
cost of padding (Section III-E)."

FIG. 6 -- Bag Identity-Recovery Flow
-----------------------------------------
Referenced: Section III-F.
Type: Flowchart.
Tool: draw.io.
Content: A decision flow starting from "New bag track ID detected":
  New bag ID -> Is there a vanished bag (in tracked_bags or the
  recently_evicted_bags echo buffer) within 80px?
    -> YES -> Recover state/timer/owner_id from the vanished entry onto the
       new ID (cite bugs_and_debugs.txt #29 in a small annotation -- this is
       literally the fix for that item)
    -> NO -> Initialize fresh: state=ATTENDED, timer=0
  A second, parallel small flow branching off "bag goes missing (dropout)":
  is_carried? -> YES -> is displacement over the recent position-history
    window above the stationary threshold? -> YES (genuinely still moving
    with someone) -> short grace window, then evict to echo buffer if still
    missing / NO (actually stationary, reclassify placed) -> long
    persistence window, no eviction on dropout alone
  This second branch is the project's most-revised piece of logic (bugs
  #32/#33/#34/#35/#36 in bugs_and_debugs.txt all touch it) -- it is worth
  getting exactly right in the diagram rather than simplifying it away,
  since it is one of the more defensible, discussable pieces of engineering
  in an oral defense.
Caption: "Fig. 6. Identity-fragmentation-aware bag state recovery. A new
track ID within a small radius of a recently-vanished bag inherits its
accumulated state rather than resetting it (Section III-F)."

FIG. 7 -- Event Log / MCP Server Architecture
--------------------------------------------------
Referenced: Section III-G.
Type: Two-process block diagram, deliberately drawn to emphasize separation.
Tool: draw.io.
Content: Two clearly separate boxes/columns with NO arrow directly
connecting them to each other -- both connect only to a shared cylinder
labeled "SQLite (event log)" in between:
  Left box: "Live Video Pipeline (main.py)" -- write-only arrow into the
  SQLite cylinder, labeled "state-change events only, fire-and-forget."
  Right box: "MCP Server (mcp_server/server.py)" -- read-only arrow out of
  the SQLite cylinder, labeled "list_runs / list_alerts / get_track_history
  / get_run_summary."
  A small annotation: "No shared process or thread. Neither can block or
  crash the other."
Caption: "Fig. 7. Event log and MCP server architecture. The two processes
communicate only through a shared SQLite file; the MCP server never
observes the live video loop directly (Section III-G)."

FIG. 8 -- Real-Footage Defect-Discovery Methodology
---------------------------------------------------------
Referenced: Section V-D.
Type: Flowchart / cyclic process diagram.
Tool: draw.io.
Content: A loop, not a straight line (the re-verification step feeding back
is the point):
  Reported/observed symptom on real footage
    -> Direct frame-by-frame pipeline instrumentation (NOT visual inspection
       alone -- label this distinction explicitly, it is the paper's actual
       methodological claim)
    -> Root cause identified
    -> Fix implemented + regression test added
    -> Re-verify against the SAME real footage
    -> [loop back arrow] "Insufficient? Back to instrumentation" (label this
       loop-back arrow specifically -- this happened twice this project,
       see bugs_and_debugs.txt #34/#35, and is worth showing as a real path
       in the diagram, not just a hypothetical one)
    -> [forward arrow, once sufficient] Fix accepted, defect log entry
       written
Caption: "Fig. 8. Real-footage defect-discovery methodology. Two of this
project's fixes were found insufficient at the re-verification step and
required a second root-cause pass before being accepted (Section V-D)."

PART 2 -- ADDITIONAL DIAGRAMS (not cited in the paper; useful for the demo,
the oral defense, and general documentation)
--------------------------------------------------------------------------------

DIAGRAM A -- Person State-Resolution Priority
-----------------------------------------------
Why this exists separately from Fig. 4: Fig. 4 shows how the suspicious-
activity flags themselves are computed; this diagram shows the separate,
smaller but frequently-asked-about piece of logic that decides which ONE
label actually gets displayed when multiple flags are true simultaneously
(resolve_person_state() in src/tracking.py). This is directly what
bugs_and_debugs.txt #23 fixed (an intrusion alert could previously be
silently overwritten by a panic spike) and is a strong, concrete answer to
"how do you handle conflicting signals" if asked at a defense.
Type: Simple ranked-priority diagram (a vertical stack, top = highest
priority, with a note that only the topmost TRUE flag is ever displayed).
Tool: draw.io or even a plain table if a diagram feels like overkill here.
Content:
  1. intruder_flag  -> INTRUDER   (highest priority)
  2. panic_flag     -> PANIC
  3. kinematic_suspicious_flag OR limb_suspicious_flag -> SUSPICIOUS_ACTIVITY
  4. (none of the above) -> NORMAL (default)
Suggested caption if added to a slide deck: "Person state is resolved from
four independent flags by fixed priority, so a lower-priority signal can
never silently mask a higher-priority alert."
Recommendation: consider promoting this to Fig. 9 in the paper itself if a
future revision adds a dedicated paragraph on state-priority resolution to
Section III-D -- it is currently described in prose there but not diagrammed.

DIAGRAM B -- Frame-by-Frame Sequence Diagram
------------------------------------------------
Why: Fig. 1 shows the architecture at rest; this shows the actual temporal
order of operations within a single processed frame, which is a common
follow-up question ("walk me through what happens for one frame") in a
defense setting that Fig. 1 alone doesn't fully answer.
Type: UML-style sequence diagram (actors/lifelines: VideoCapture, YOLOv8n,
ByteTrack, TrackingStateMachine, PoseModel (conditional), OverlayRenderer,
EventLog).
Tool: Mermaid (`sequenceDiagram` is a natural fit and quick to iterate) or
draw.io.
Content, in order: capture frame -> letterbox resize -> model.track() call
(YOLOv8n + ByteTrack together, since ultralytics bundles them in one call)
-> update_tracking_states() (updates all three objectives' state) ->
get_pose_gated_person_ids() check -> [conditional lifeline activation] pose
model inference only if gated-in -> draw overlays -> log_state_changes()
(only if a state actually changed since last frame) -> display/next frame.
Mark the pose-model step as an optional/conditional activation (a dashed
box or alt-fragment in UML sequence diagram convention) to visually
reinforce that it does not run every frame.

DIAGRAM C -- Precision/Recall/ID-Switches Comparison Chart
----------------------------------------------------------------
Why: Table II and Table III already report these numbers in the paper; a
chart is not needed there, but is genuinely useful for a slide deck or
viva, where a visual comparison lands faster than a table read aloud.
Type: Grouped bar chart.
Tool: matplotlib, reading directly from benchmark/*.csv (do not hand-type
these numbers into a charting tool -- they should be generated from the
same source data the paper's tables cite, so the chart and the paper can
never silently drift apart).
Content: Two groups of bars (moderate-distance clip vs. wide-overview
clip), each group showing precision, recall, and (for the moderate-distance
clip only) ID switches for both baseline and custom configurations. Two
side-by-side subplots (one per clip) is likely cleaner than trying to fit
both distance regimes onto one shared axis, given how different the recall
values are between them (56.4%/54.9% vs. 5.6%/3.5%) -- a single shared
y-axis would make the wide-overview bars nearly invisible.

DIAGRAM D -- Latency Breakdown Chart
------------------------------------------
Why: Same rationale as Diagram C -- Table IV already has the numbers; a
chart communicates the "under 1%" claim faster in a live presentation.
Type: Stacked horizontal bar (a single bar, detection latency and reasoning
latency stacked, so the reasoning-layer sliver is visually obvious as
almost nothing next to the detection block) rather than two separate bars,
which would need a log scale to show the reasoning layer at all and would
undercut the "it's negligible" point the chart exists to make.
Tool: matplotlib, reading from benchmark/*.csv.
Content: One horizontal bar, ~106.2ms detection segment plus a ~0.6ms
reasoning segment, annotated with the percentage split directly on the bar.

DIAGRAM E -- Dataset Coverage Panel
-----------------------------------------
Why: The paper names six real-world datasets (Section IV-A); a single
figure showing one representative frame from each makes the breadth of
real-footage testing immediately legible in a demo or defense, in a way
that a comma-separated list of dataset names in the text does not.
Type: 2x3 (or 3x2) grid of real video frames, one per dataset, each with a
small caption underneath naming the dataset and which objective it was used
to validate.
Tool: Real screenshots, one per dataset (VIRAT, CDnet, ABODA, AVSS 2007,
UCF-Crime, Avenue), assembled into a grid in any basic image tool.
Content: For each panel, prefer a frame that visibly shows the relevant
objective's overlay active (a bounding box, a polygon, a state label) over
a plain unannotated frame -- this does double duty as both a dataset-scope
figure and a working-system proof.

DIAGRAM F -- MCP Query Flow: What's Real vs. What's Simulated
--------------------------------------------------------------------
Why: This came up directly and repeatedly while preparing the demo (see
please_study.txt Section 12) -- it is worth having a diagram ready that
draws the exact line between the tool layer (real, verified) and an actual
LLM client (not yet connected), since this is a question likely to be asked
directly and a diagram answers it more precisely than a verbal explanation
alone.
Type: Two-row comparison flowchart.
Tool: draw.io.
Content:
  Row 1, labeled "What actually runs today (demo_mcp_query.py)": a human
  (drawn as a small stick figure or labeled box, not omitted) -> writes a
  hardcoded Python call sequence -> MCP tool functions -> SQLite -> printed
  output. Label this row clearly as "verified, real, deterministic."
  Row 2, labeled "What MCP enables but is not yet built": a human -> types
  a natural-language question -> [a box literally labeled "LLM (not yet
  connected)"] -> the LLM reasons about which tool to call -> MCP tool
  functions -> SQLite -> synthesized natural-language answer. Label this row
  "infrastructure-ready, not yet exercised."
  Both rows should visually converge on the SAME "MCP tool functions ->
  SQLite" boxes, to make the point that the tool layer itself is identical
  in both cases -- only what sits in front of it differs.

NOTES
--------------------------------------------------------------------------------
- Every real-frame figure above (2, 5, and Diagram E) should be captured
  from the live pipeline as it actually runs (main.py, with the window
  visible), not staged or mocked up. Several of this project's own
  documented defects were specifically about visual overlay bugs
  (bugs_and_debugs.txt #16, #20, #26, #27, #32-#36) -- a genuine screenshot
  is also, quietly, additional proof that those fixes hold.
- None of Part 1's 8 figures are optional if this paper is taken to actual
  submission; a reviewer will notice "Fig. 3" cited in text with no
  corresponding image. Part 2 is prioritized (A and F are the most likely
  to actually get asked about live; C/D/E are the most useful for slides
  specifically, and are the easiest to skip if time is short).
- If time allows only a handful of these before a defense or demo, prioritize
  in this order: Fig. 1 (nothing else makes sense without the big picture),
  Fig. 3 (the single most-discussed piece of logic in this project), Fig. 8
  (this is the paper's actual methodological contribution, not a nice-to-
  have), Diagram A (fast to make, answers a near-certain question), and
  Diagram F (same reasoning, given how much this exact question came up
  while preparing the demo).
